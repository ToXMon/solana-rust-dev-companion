Use this module when turning homework, examples, capstones, or the Solana Rust Dev Companion into public proof.

## Core idea

Shipping is table stakes.
Being found, trusted, remembered, and vouched for is the scarce asset.

A Solana Rust learner should treat every serious homework as both code and public proof.
The goal is not empty promotion.
The goal is to make the work legible to builders, reviewers, grant committees, teammates, and future employers.

## Positioning

Bad:

> Web3 enthusiast | Rust | AI | Builder | Dreamer

Better:

> Rust/Anchor dev building Solana program exercises. Shipping DeFi examples, tests, and safety notes in public.

Better repo positioning:

> Solana Rust Dev Companion: build small Anchor programs, prove them with tests, explain the safety tradeoffs, and turn each project into a portfolio artifact.

## Narrative pillars

Use these pillars for posts, README updates, demos, and project pages.

- Build: what was implemented.
- Safety: what risks were handled.
- Learning: what was confusing, broken, or fixed.
- Ecosystem: why this belongs on Solana.
- Help: how the artifact helps another builder.

## Homework launch checklist

### Before launch

- [ ] README has a one-paragraph non-technical summary.
- [ ] README has commands someone can run.
- [ ] Tests pass.
- [ ] A test screenshot or terminal proof exists.
- [ ] A 60-second demo script exists.
- [ ] One visual exists: screenshot, GIF, architecture diagram, or short video.
- [ ] The post bank includes a hook, demo, technical detail, safety detail, lesson learned, and ask.
- [ ] Five to ten relevant supporters, peers, or reviewers are identified.
- [ ] The ask is specific: feedback, review, intro, star, contribution, or hackathon teammate.

### Launch day

- [ ] Post the demo first, not a vague announcement.
- [ ] First line states the outcome plainly.
- [ ] Include proof link: repo, tests, screenshot, or demo.
- [ ] Reply with technical context instead of stuffing everything into the main post.
- [ ] Ask supporters before or at launch.
- [ ] Spend 30 to 60 minutes replying thoughtfully to comments and adjacent conversations.

### After launch

- [ ] Turn questions into README improvements.
- [ ] Turn bugs into a short what-broke-and-what-I-fixed post.
- [ ] Add one docs, tests, or example PR to another ecosystem repo.
- [ ] Thank reviewers publicly.
- [ ] Save high-signal replies into the next content plan.

## 30-day visibility plan

### Week 1 - profile and proof surface

- Rewrite bio using: `I am [specific builder] building [specific Solana thing] for [specific audience/outcome].`
- Pin the best proof: repo, demo, or build log.
- Add screenshots or diagrams to the project page.
- Write one plain-English explanation of the project.

### Week 2 - lane and daily posting

- Pick one lane: Solana Rust, Anchor DeFi, program security, indexing, or developer tooling.
- Post one small item daily from real work.
- Reply to relevant Solana developer conversations.

### Week 3 - show the work

- Publish one demo or walkthrough.
- Land one small public contribution if possible.
- Write one technical note from a bug or design tradeoff.

### Week 4 - help loudly, then ask

- Help five people publicly.
- Review a small example or docs issue.
- Make one specific ask.

## No-slop AI marketing rule

Agents may help with angles, outlines, editing, repurposing, demos, and launch plans.
Agents must not invent traction, claims, partners, users, benchmarks, or vibes.

Good prompt:

> You are editing my post, not inventing one. Use only the facts below. Keep my voice direct and technical. Avoid hype, emojis, generic claims, and engagement bait. Produce three versions: plain, technical, and founder-friendly. Facts: [repo summary, test output, demo notes, target audience, desired ask].
